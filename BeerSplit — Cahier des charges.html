Section 01

Contexte
& vision produit.

Le problème

Une tireuse à bière à la maison change la donne : on tire ses bières à volonté, on partage le fût. Mais à la fin, personne ne sait qui a bu combien. Le propriétaire de la tireuse avance les 150-200 € du fût, et la répartition se fait à la louche — généralement à son désavantage.

Les apps de partage de dépenses (Tricount, Splitwise) ne sont pas adaptées : elles partagent par parts égales, alors qu'un gros buveur et un buveur occasionnel n'ont pas la même consommation. Aucune solution dédiée n'existe pour le suivi en temps réel d'un fût.

La promesse

Chaque bière comptée. Chaque centime juste. Aucune dispute.

Objectifs

01 / SIMPLE
2 taps pour compter
L'action principale (compter une bière) doit prendre moins de 3 secondes, même la 8e bière de la soirée.
02 / JUSTE
Prorata du volume
Le calcul est transparent et basé sur le volume réel consommé, pas sur des parts égales arbitraires.
03 / SOCIAL
Compétition & souvenir
Le classement et les stats transforment chaque soirée en moment, pas seulement en comptabilité.

Hors-périmètre v1

  • Paiement intégré (le calcul est fait, le règlement reste manuel via virement / Lydia / cash).
  • Version Android et Web (envisagé v2).
  • Intégration matérielle avec une tireuse connectée (envisagé v3).
  • Mode bar professionnel / B2B.

Section 02

Qui
l'utilise.

Trois personas couvrent les rôles possibles dans une session. Un même utilisateur peut endosser plusieurs rôles d'une session à l'autre.

H

L'hôte — Pierre, 34 ans

Possède la tireuse · crée la session · règle l'achat du fût

Besoins : ne pas avancer les frais à fonds perdus, savoir précisément combien chaque copain lui doit, relancer sans gêne. Frictions actuelles : calcule de tête, oublie qui a bu, n'ose pas réclamer. Usage clé : écrans 03 (création) et 08 (split final).

B

Le buveur régulier — Marco, 31 ans

Invité fréquent · compétiteur · attentif au classement

Besoins : savoir où il se situe, ne pas être lésé, payer ce qu'il doit sans plus. Frictions : trouve injuste de payer comme quelqu'un qui a bu deux bières. Usage clé : écrans 04 (compteur), 06 (classement), 07 (stats annuelles).

O

Le buveur occasionnel — Léa, 29 ans

Invitée ponctuelle · sobre ou modérée · à l'aise socialement

Besoins : ne pas se sentir obligée de boire pour « rentabiliser », payer juste sa part. Frictions : les pots collectifs où elle paye autant que ceux qui boivent quatre fois plus. Usage clé : rejoindre par code (écran 02), valider sa note (écran 08).

Contexte d'usage

Soirée maison

5 à 10 personnes, 2 à 4 heures, tireuse domestique 20-30 L. Cas principal.

Apéro résidence / coloc

Fût mutualisé entre colocataires, plusieurs sessions sur la semaine.

Soirée extérieure

Anniversaire, vacances, fête de village. Une session ponctuelle, beaucoup de participants.

Hypothèses techniques d'usage

  • Une seule session active par utilisateur à un instant T.
  • Wifi domestique disponible ; mode offline souhaité (compteur local, sync à la reconnexion).
  • Téléphone à proximité de la tireuse, posé sur un meuble — bouton +1 visible et large (≥ 64 pt).
  • Soirée typique : 60-80 bières comptées, 6-8 participants, durée 2h30.

Modèle de données (PostgreSQL)

-- users
users ( id uuid pk, email, password_hash, apple_sub, first_name, avatar_url, language, created_at, deleted_at )

-- sessions (fûts)
sessions ( id uuid pk, code char(6) unique, host_id → users, brewery, beer_name, abv, volume_ml int, price_cents int, tapped_at, ended_at, status enum('active','ended','cancelled') )

-- participants (n:n)
participants ( session_id → sessions, user_id → users, joined_at, left_at, role enum('host','guest'),
  pk(session_id,user_id) )

-- beers (comptages)
beers ( id uuid pk, session_id → sessions, user_id → users, size enum('demi','pinte','serieuse','custom'), volume_ml int, counted_at, counted_by → users, cancelled_at )

-- settlements (split final, gelé)
settlements ( session_id → sessions pk, computed_at, total_volume_ml, snapshot_json, breakdown_json )

Formule du split (référence canonique)

volume_total_bu = Σ beers.volume_ml (non annulés)
dû(user) = prix_fût × (volume_bu_user / volume_total_bu)
// Arrondi à 0,10 € au plus proche, l'hôte absorbe l'écart d'arrondi.

Performance,
sécurité, conformité.

Exigences de performance

IDExigenceCible
NF1.1Temps de démarrage cold start (P95)≤ 1,5 s
NF1.2Latence d'un comptage (tap → confirm visuel)≤ 150 ms
NF1.3Latence réseau d'un comptage (POST /beers, P95)≤ 400 ms
NF1.4Propagation WebSocket d'un événement≤ 500 ms entre participants
NF1.5Fonctionnement offline complet pour le comptage100 % des opérations
NF1.6Taille du binaire iOS≤ 30 MB

Sécurité

  • Mots de passe hashés en bcrypt (cost ≥ 12) ou Argon2id. Jamais en clair en base ni en log.
  • Tokens JWT de session courte durée (15 min) + refresh token rotatif (30 j) stockés en Keychain iOS.
  • HTTPS uniquement (TLS 1.3). Certificate pinning sur l'API en production.
  • Rate limiting côté backend : 60 req/min/IP, 10 tentatives de login/heure/email.
  • Codes de session à 6 caractères : alphabet sans ambiguïté (pas de 0/O/I/1), expiration 24 h après la fin de session.
  • Idempotence-key obligatoire sur POST /beers pour éviter les doubles comptages.
  • Audit log des actions sensibles (suppression compte, clôture session).

Conformité RGPD

  • Hébergement des données en UE (Frankfurt ou Paris).
  • Page « Mes données » : export JSON de tout ce que l'app contient sur l'utilisateur.
  • Suppression de compte effective sous 30 j ; les sessions passées sont anonymisées (prénom → « ex-participant »).
  • Consentement explicite pour les analytics au premier lancement (opt-in, refus par défaut).
  • Pas de partage de données à des tiers en v1.
  • Mentions légales, CGU et politique de confidentialité dans le profil + lien depuis le sign-up.

Internationalisation

  • Strings externalisés via String Catalogs (.xcstrings).
  • Langues v1 : FR (par défaut), EN.
  • Formats monétaires et dates : locale système (€ FR par défaut).
  • Aucun texte « en dur » dans le code.

Observabilité & qualité

  • Couverture de tests unitaires ≥ 60 % sur les calculs (split, agrégats).
  • Tests UI smoke sur les 3 flux principaux.
  • CI : build + tests + lint à chaque PR (Xcode Cloud ou GitHub Actions).
  • Dashboards Sentry / PostHog en production. Alerte si crash-free rate < 99,5 %.
